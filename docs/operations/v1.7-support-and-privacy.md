# v1.7 support and privacy operations

This guide gives maintainers a consistent answer for common v1.7 questions and
keeps public support language aligned with the implementation. It supplements
the in-app policy in [`PrivacyPolicyModal.tsx`](../../src/components/PrivacyPolicy/PrivacyPolicyModal.tsx)
and the engineering record in
[`umami-telemetry-privacy-operations.md`](./umami-telemetry-privacy-operations.md).

## First-response triage

When a user reports a release problem, record the release channel, app version,
browser, device class, viewport, account state, route, approximate time, and
whether the failure is reproducible after a reload. Do not request forecast
contents, coordinates, exported files, email addresses, or authentication
tokens unless a separate support process explicitly requires them.

Classify the report before responding:

| Report | First check | Safe support response |
| --- | --- | --- |
| Blank map, crash, or broken route | Browser console/Sentry event and route | Preserve the last known-good forecast state; collect reproduction steps and viewport |
| Missing or stale radar, satellite, report, or reference data | Provider/source state and valid time | Explain that upstream data can be empty, stale, delayed, or unavailable; do not call it data loss without evidence |
| Auto-TSTM unavailable | Target exposure, cache health, supported day, and deployment capability | It is cached guidance on supported rollout targets; unavailable or stale results must not be applied silently |
| Custom product locked | Signed-in state, entitlement, and expired-premium state | Local forecasting remains available; hosted reusable products and writes follow the premium boundary |
| Forecast missing after account deletion | Whether the forecast was local or hosted | Account deletion removes hosted data but intentionally leaves local/offline saves untouched |
| Analytics/privacy question | Local opt-in state and event boundary | Analytics are optional, disabled by default, pseudonymous, and separate from Firebase identity |

## v1.7 limitations to state plainly

- NOAA DAT evidence is supplemental prototype evidence and does not replace
  official verification sources.
- Auto-TSTM is guidance, not an automatic forecast decision. Preview, cancel,
  apply, undo, stale-result, and unavailable states are intentional.
- Monitor reference layers are optional context. Their source metadata,
  attribution, valid time, and stale/error state must remain visible.
- Built-in Rainfall and Tropical AOI styles are catalog entries, not editable
  user-owned reusable products.
- Beta-only or disabled workstreams may appear in release documentation while
  remaining unreachable on staging or production.
- GFC does not currently promise a fixed event-level telemetry retention window.

## Privacy requests

For an analytics access or deletion request, ask for only the approximate date
and time, browser/device, route or event description, and whether optional
analytics was enabled. Explain that Umami records are pseudonymous and are not
linked to Firebase account identity, so a request may not be locatable from an
email address alone.

Route privacy questions and manual deletion requests to
`alex@weatherboysuper.com`. Record the request and response outside the
analytics system. Never promise that deleting a Firebase account automatically
deletes an unrelated pseudonymous analytics record.

## Escalation record

Every release-blocking report should include:

- Release channel and exact version or commit.
- Reproduction route and steps.
- Browser, device, viewport, and account/entitlement state.
- Whether the issue affects local data, hosted data, billing, upstream data, or
  only presentation.
- Screenshot or recording only when it does not expose private forecast content.
- Related issue number and whether the issue blocks normal forecasting.

Use the REL-02 acceptance matrix for reproducible browser coverage and the
REL-01 exposure matrix before changing a feature's target state.
