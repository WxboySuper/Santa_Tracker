# v1.7 integration and exposure matrix

**Status:** release planning artifact  
**Target release:** v1.7.0  
**Review cadence:** Revalidate whenever the registry or v1.7 release target changes
**Owner:** WxboySuper

This document is the cross-feature release view for v1.7. It describes which
surfaces are available on each build target, what must be proven before a
target is enabled, and which features remain intentionally unavailable.

The typed registry in [`src/config/featureExposure.ts`](../../src/config/featureExposure.ts)
remains the executable source of target exposure. This document does not enable
features by itself. A production change requires a separate reviewed exposure
change and release evidence.

## Exposure vocabulary

| Target | Meaning | Release use |
| --- | --- | --- |
| `local` | Maintainer and test development build | Feature implementation and focused tests |
| `beta` | Hosted prerelease built from reviewed `main` | Cross-feature and tester validation |
| `staging` | Production-like rehearsal build | Candidate smoke and operational checks |
| `production` | Stable public deployment | Only explicitly approved surfaces |

## Enablement order

1. Keep the registry and exposure-policy validation passing.
2. Complete the workstream implementation and disabled-side-effect evidence.
3. Merge the reviewed work into `main`; do not treat a merge as production enablement.
4. Build a beta release from the exact reviewed `main` commit.
5. Run the v1.7 desktop/mobile acceptance matrix and review beta health.
6. Deploy staging for the candidate when production-like infrastructure checks are needed.
7. Approve only the rows explicitly supported by the candidate evidence.
8. Promote the approved stable version through the reviewed stable-release workflow.

## Production decision record

The REL-04 release-candidate record must include:

- The `main` commit and beta version tested.
- The generated exposure report and any target-specific differences.
- The acceptance-matrix result and manual responsive evidence.
- Sentry health review for beta and staging.
- Any approved production exposure changes, with owner and rollback path.
- Confirmation that disabled rows remain disabled and produce no route, navigation,
  worker, subscription, fetch, or server-handler side effects.

The default v1.7 production posture is therefore: core product surfaces on,
temporary or experimental surfaces off unless separately approved, and no
production exposure inferred from beta availability.
