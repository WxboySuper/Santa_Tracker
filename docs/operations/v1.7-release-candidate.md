# v1.7 release-candidate runbook

**Target:** v1.7.0  
**Integration source:** reviewed `main` commit  
**Owner:** WxboySuper

This runbook closes the gap between a merged REL stack and a production
release. It is intentionally evidence-gated: a local build or passing PR does
not by itself authorize production exposure.

## Local evidence captured before PR submission

The REL stack has already produced these local results:

| Gate | Result | Evidence |
| --- | --- | --- |
| Feature-exposure policy | Pass | `pnpm run validate:feature-exposure` — 13 registry features and all policy checks passed |
| Exposure tests | Pass | `pnpm run test:exposure` — 25 Node tests and 8 Jest suites / 55 tests passed |

and billing service was not running. Hosted beta and staging checks must repeat
the matrix against their real service boundaries.

## Candidate procedure

1. Confirm the live PR bases with `gh stack view` and each required check with
   `gh pr checks <number>`, then merge REL-01, REL-02, REL-03, and REL-04 into
   `main` in stack order.
2. Record the final merged `main` SHA and stop unrelated merges while the
   candidate is being tested.
3. Create a beta prerelease from `main` using **Create Beta Release** with
   `RELEASE-BETA`. Record the generated `v1.7.0-beta.N` tag and deployment run.
4. Run the REL-02 acceptance matrix against the hosted beta URL on desktop,
   portrait phone, and constrained landscape. Test signed-out/free, premium,
   expired-premium, and disabled-feature states where applicable.
5. Review the generated exposure report against
   [`v1.7-exposure-matrix.md`](./v1.7-exposure-matrix.md). Confirm no feature
   moved into production exposure without an explicit approval.
6. Run **Deploy Staging** with the same immutable commit and
   `DEPLOY-STAGING`. Repeat smoke, accessibility, map, source-state, and
   production-like API checks.
7. Review beta and staging Sentry health, browser console failures, release
   logs, and upstream data-state warnings. Classify expected provider outages
   separately from product failures.
8. If all blockers are resolved, run **Prepare Main Stable Promotion** for
   `1.7.0` from the reviewed `main` SHA and review the generated promotion PR.
9. After that PR merges, run **Bootstrap Stable Release Line** with the exact
   merged SHA, version `1.7.0`, and `BOOTSTRAP-STABLE`.
10. Review the resulting `stable/1.7.x` branch, then run **Create Stable
    Release** with `RELEASE-STABLE`. The published stable release activates
    the production deployment workflow.
11. Verify the production URL, core routes, login boundary, forecast save/load,
    Monitor, Verification, privacy policy, and `/updates` page. Record the
    release tag, deployment run, smoke timestamp, and Sentry health.

## Command references

```powershell
gh workflow run release-beta.yml --ref main -f confirmation=RELEASE-BETA
gh workflow run deploy-staging.yml --ref main -f ref=<merged-main-sha> -f confirmation=DEPLOY-STAGING
gh workflow run prepare-stable-promotion.yml --ref main -f source_ref=<merged-main-sha> -f version=1.7.0 -f confirmation=PREPARE-STABLE-PROMOTION
gh workflow run bootstrap-stable-release.yml --ref main -f source_ref=<promotion-merge-sha> -f version=1.7.0 -f confirmation=BOOTSTRAP-STABLE
gh workflow run release-stable.yml --ref main -f ref=stable/1.7.x -f confirmation=RELEASE-STABLE
```

Use `gh run list`, `gh run view <run-id>`, and the hosted browser checks after
each workflow. Do not report promotion as complete from a queued or merely
successful workflow dispatch; verify the deployed URL and release artifact.

## Rollback and support readiness

- Keep the previous stable tag and deployment manifest identified before the
  production run.
- If production smoke fails, stop further promotion, preserve the failing
  release evidence, and use the intentional production deployment workflow with
  a known stable ref and reviewed manifest.
- Do not deploy arbitrary `main` or a beta tag directly to production as an
  emergency shortcut.
- Link user-facing incidents to
  [`v1.7-support-and-privacy.md`](./v1.7-support-and-privacy.md) and record
  whether the issue affects local data, hosted data, billing, upstream data, or
  presentation only.

## Closure rule

Close REL-04 and parent tracker #435 only when:

- The four REL PRs are merged.
- Beta and staging acceptance evidence is attached.
- The exposure report matches the approved target state.
- Stable release and production smoke evidence are recorded.
- No unresolved P0/P1 release blocker remains.
- Rollback and support notes are ready for maintainers and users.
